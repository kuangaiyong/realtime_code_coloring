# 被测服务跑在容器里时的实时染色

> 日期 2026-09-02 ｜ 仓库 `C:\code\realtime_code_coloring` ｜ 起点 dev 分支 `cc069b6`（v0.9.0 已发布）

> **本方案未经真实验证。** 编写这份文档的机器是阿里云虚拟机，没有 Docker
> 也装不了。按项目规则 2（禁止 mock、必须真实验证），**它不能被当成「已验证方案」**——
> §七 逐条列出了哪些能在裸机上验、哪些必须等容器环境。

---

## 一、问题

平台与被测服务之间**只有两条通道**：

| 通道 | 用途 | 容器化之后 |
|---|---|---|
| 网络 | 连探针端口，拉覆盖数据 | 端口映射即可，**不是问题** |
| **文件系统** | **读编译产物**，解析行号 | **平台看不见容器内的文件** |

第二条是全部矛盾所在。而它的依赖逐语言不同：

| 语言 | 平台需要容器里的什么 | 为什么 |
|---|---|---|
| **Go** | **什么都不要** | meta / counters 全从网络来，自包含 |
| Java | `classes-dir`（`.class`） | JaCoCo 要靠字节码把探针 id 还原成行号 |
| Rust | `rust-binary`（产物本身） | 行号在产物自带的 coverage mapping 里 |
| C++ | `.gcno` **且 gcov 要在源码根下跑** | `.gcno` 是编译期产物，记的是相对源码名 |

**所以 Go 今天就能在容器里跑**：改 Dockerfile 加
`-cover -covermode=atomic -tags=goverage`、映射探针端口、传 `COVERAGE_BUILD_ID`，
平台侧一行不用改。卡住的只有 Java / C++ / Rust。

源码与 git 不在此列：染色页要显示源码、Go 要剔空行、C++ 的 gcov 要在源码根下跑、
增量口径要 `git diff` —— 但这些平台可以自己 clone 仓库并 checkout 到对应 commit，
不必来自容器。`GitService` 已经是这么用 `repoDir` 的。

### 1.1 探针注入不是问题，但要改构建

Java 的 agent 可以用 volume 挂进容器、只改 `JAVA_OPTS`，**镜像不用重建**；
Go / C++ / Rust 必须带插桩重新编译，**得改 Dockerfile**。
本方案的前提是构建流程可改，因此四种语言都能接。

注意这与 §3.1 说的是两件事：**挂 agent 进去（能做）** 与
**让 agent 把 classes 交出来（做不到）**。前者是启动参数，后者要改 JaCoCo 的协议。

## 二、部署形态与本方案的适用范围

| 形态 | 产物怎么给平台 | 要改什么 |
|---|---|---|
| 平台与容器同宿主机 | volume 把产物目录挂到宿主机 | **代码一行不改**，配置指向挂载点 |
| 平台自己也在容器里 | 与被测容器共享 volume | 同上，但平台镜像要带 Go / gcov / llvm 工具链 |
| **完全隔离（本方案）** | **构建时按 buildId 推给平台** | 见下 |

前两种形态是配置问题，不需要这份设计。**本方案只解决第三种**：
平台与被测容器跨主机 / 跨集群，只有网络可达。

## 三、已确认的决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **产物由构建流程推给平台**，不由探针交出 | 见 §3.1 |
| 2 | **产物以 `buildId` 为唯一索引** | 见 §3.2，这是整个方案的地基 |
| 3 | **取不到产物一律拒绝出报告**，不降级 | 见 §3.3 |
| 4 | **`-dirty` 构建拒绝上传** | 见 §3.4 |
| 5 | 两种产物来源共存，按项目选（`local` / `uploaded`） | 裸机部署与现有 8 实例验证链路一行不动 |
| 6 | 每个项目保留最近 N 个 buildId 的产物，超出删最旧 | 简单、可预测，不依赖时钟 |

### 3.1 为什么不让探针交出产物

探针与运行中的进程天然同源，让它顺便把产物也交出来，是个很有吸引力的方案 ——
不可能拿错版本，也不必改 CI。

**但它要拿探针的极小换。** 自研的三个探针（Go / C++ / Rust）现在分别是
72 / 215 / 261 行的独立编译单元，零依赖是它们反复强调的价值；Rust 那个还背着
「全程只调 Win32 API、一句 CRT 都不碰」的硬约束（它用 MinGW 编译却要链进
MSVC ABI 的产物）。加一段「打包目录并经 socket 交出」会直接破坏这个约束，
而探针是跑在**别人的生产构建**里的东西 —— 它越小、依赖越少，别人才越敢用。

Java 那一侧更走不通：用的是 **JaCoCo 官方 agent**，它的 tcpserver 协议只交
exec 数据，平台不能往里加一条「把 classes 也给我」的指令 —— 除非自己写一个
Java agent 来替换它，而那是比本方案大得多的一件事。

构建流程可改的前提下，这个代价不值得付。

### 3.2 为什么必须按 buildId 索引

**这不是实现细节，是整个方案成立的前提。**

产物若按固定路径存（如 `artifacts/{projectId}/classes`），就会出现：
推上去的是 commit A 的产物，容器里跑的是 commit B ——
平台拿 A 的字节码去解 B 的探针数据，**算出行号错位却看起来完全正常的报告**。
这正是本项目最不能犯的错。

按 `buildId` 索引之后，取不到就是明确的「这个构建的产物没上传」。
而 `buildId` 恰好已经是实例自报的那个值（`BuildVersion`，格式 `^([0-9a-f]{40})(-dirty)?$`），
两端天然对齐，不需要新的版本标识。

### 3.3 取不到产物时拒绝出报告

缺产物时若跳过那门语言，界面上表现为「这些代码没被调用过」——
与真相完全相反，而且看不出是缺产物。

所以走 `ANALYZE_ERROR`，错误信息里**点名缺的是哪个 buildId 的哪种产物**，
与 `cpp-objects-dir` 指错目录时的现有行为一致（核心功能 #13）。

### 3.4 为什么拒绝 `-dirty` 构建

`-dirty` 意味着同一个 commit 可以对应无数份不同的产物。
允许上传就等于允许「同一个 key 指向不同内容」，取出来的可能不是这个容器加载的那份 ——
仍然是行号错位且看不出来。

平台本来就对 `-dirty` 拒绝出增量报告（§一），这里是同一条原则向产物存储的延伸。
上传接口直接回 400 并说明原因。

## 四、设计

### 4.1 数据流

```
CI 构建镜像
  ├─ 编译产物（.class / .gcno / 二进制）
  └─ POST /api/artifacts/{buildId}?lang=java        ← 新增
                                    │
被测容器（探针端口映射出来）             ▼
  └─ 自报 buildId ──────────► 平台：按 buildId 取产物 ─→ 归一化 ─→ 染色
                                    │
                             git checkout 到该 commit
                             （源码、增量 diff；GitService 已有）
```

### 4.2 新增与改动的单元

| 单元 | 职责 | 依赖 |
|---|---|---|
| `ArtifactStore`（新增） | 按 buildId 存取产物；保留最近 N 个 | 磁盘 |
| `ArtifactController`（新增） | 上传 / 查询 / 删除；校验 buildId 与大小 | `ArtifactStore` |
| `ProjectConfig`（改） | 加 `artifactSource: local \| uploaded` | — |
| `ProjectRuntime`（改） | **按模式解析出产物路径**，再传给 Analyzer | `ArtifactStore` |

**四个 Analyzer 一行不改**（Go 的本来就不碰产物，另外三个也不用动）。

> **2026-09-03 修正：这里原先写的「先按模式解析路径、再传给 Analyzer」只对 Java 成立。**
> 实施前核对代码发现，三个 Analyzer 拿产物路径的方式并不一致：
>
> | Analyzer | 签名 | 产物路径从哪来 |
> |---|---|---|
> | `CoverageAnalyzer`（Java） | `analyze(execStore, File classesDir, String sourceRoot)` | **外部传入** |
> | `CppCoverageAnalyzer` | `analyze(List<byte[]> dumps)` | 自己读 `props.getCppObjectsDir()` |
> | `RustCoverageAnalyzer` | `analyze(List<byte[]> dumps)` | 自己读 `props.getRustBinary()` |
>
> C++ 与 Rust 压根没有接收路径的入参，「解析好再传」这条路走不通。
>
> **但结论不变，做法换一个**：这两个 Analyzer 是在 `ProjectRuntimeFactory` 里
> 用 `new CppCoverageAnalyzer(cfg, platform)` 造出来的 —— 喂给它一份
> <b>产物路径已换成解压目录的配置副本</b>即可。Analyzer 仍然不知道那个目录
> 是配置里写的还是解压出来的，分层没有被破坏。

这一条是刻意的：Analyzer 收到的始终是一个本地目录，
它不需要知道那个目录是配置里写的还是解压出来的。

产物来源属于**上游**，不该渗进归一化层。CLAUDE.md 里 P2 / P3 / P4 三次验收都在守
「接入新语言不改 Analyzer」这条分层 ——
**若实现时发现非改 Analyzer 不可，那说明这个分层判断错了，要停下来重新审，
而不是顺手改掉。**

### 4.3 存储布局

```
<artifact-root>/<projectId>/<buildId>/
  ├─ java/     classes 解压后的目录树
  ├─ cpp/      .gcno
  └─ rust/     产物二进制
```

Go 不占目录 —— 它不需要产物。

`buildId` 直接参与磁盘路径，**上传前必须用 `BuildVersion` 的正则校验**
（`^[0-9a-f]{40}$`，不接受 `-dirty`）。不校验就是路径穿越：
一个 `../../` 能让上传接口写到平台的任意位置。

### 4.4 上传接口

```
POST /api/artifacts/{buildId}?lang=java|cpp|rust
  multipart：产物打包（tar/zip）
  → 200  已存下
  → 400  buildId 格式非法 / 带 -dirty / 语言不认识
  → 413  超过大小上限
```

平台此前**没有任何文件上传**，这是第一处 —— 要显式配 multipart 上限，
不能用框架默认值（Spring 默认 1MB，一个 Rust 产物就顶穿）。

**安全边界要写清楚**：探针端口现在没有鉴权，靠「只绑回环 + 网络策略」兜着；
上传接口能**写**平台磁盘，风险高一档。本方案仍假设平台只面向内网，
但这条假设必须写进文档，而不是默认。

### 4.5 保留策略

每个项目按 buildId 的写入时间保留最近 N 个（默认 10），超出删最旧。

不按天数：一个长期不发布的服务会把自己正在跑的那份产物清掉，
而那时平台会开始拒绝出报告 —— 一个由「太久没发版」引发的故障，没人查得到。


## 七、验证边界（如实记录）

**本机没有 Docker，本方案未经端到端验证。** 能验与不能验必须分开：

### 7.1 不需要容器，裸机上就能真实验证

- 上传接口：合法 buildId 存得下、能取回、内容逐字一致
- `-dirty` 的 buildId 回 400 并说明原因
- 路径穿越（`../`、非 40 位 hex）一律拒绝
- 超过上限回 413
- 保留策略：写第 N+1 个时最旧的那个真的被删了
- **取不到产物时拒绝出报告**（`ANALYZE_ERROR` 且点名缺哪个 buildId）
- `artifact-source: local` 时行为与现在逐字一致（现有 231 条断言不回归）

以上都可以在本机跑成真实用例 —— 它们不依赖容器，只依赖「产物来自另一个目录」。

### 7.2 必须有容器环境才能验

- 容器里的探针端口映射后平台连得上
- 产物从容器构建流程推上来之后，**解出来的行号真的对**
- 跨主机的端到端染色延迟仍 ≤ 5s（核心功能 #5）
- 滚动发布期间新旧 buildId 并存时的表现

**第二条是唯一值得验的东西**，也恰恰是本机验不了的：产物传过去、
按 buildId 取回来、解出的行号与容器内实际执行的行对得上。
在此之前，这份方案只是纸面成立。

## 八、不做

- **不让探针交出产物**（§3.1）
- **不让平台按 commit 自己编译产物** —— 必须与容器内的构建完全一致才行号对得上，
  编译器版本、优化级别、路径差一点就错位，而且是静默的；平台还要装四套完整工具链。
  这把「数据可信」押在一个很难保证的前提上
- **不接制品库（Nexus / Harbor / OSS）** —— 企业环境差异太大，先用最简单的上传接口
  跑通；真有需要时它是 `ArtifactStore` 背后的一个实现，不影响上层
- **不做产物的增量传输 / 去重** —— 保留最近 10 个构建，总量可控；
  真成为问题时再说
