> 日期 2026-08-31 ｜ 仓库 `C:\code\realtime_code_coloring` ｜ 起点 dev 分支 c09936c（v0.8.0 已发布）

---

## 一、问题

### 1.1 现在只有一个指标，而且它偏乐观

IR 里只有行覆盖：`FileCoverage(coveredLines, missedLines, ratio)` 加每行一个 `status`。
`PARTIAL`（行内有分支没跑到）在染色上是黄色、看得见，但在计数时落进了 `else` 分支：

```java
if ("MISSED".equals(status)) { missed++; } else { covered++; }   // PARTIAL 被算成 covered
```

于是 `if (a && b)` 只跑了一半，这一行照样按 100% 计入行覆盖率。
**「没有分支覆盖率」的实质后果不是少一个数字，是现有的数字比真实情况乐观，
而乐观多少完全看不出来。**

需要说明的是，**这与 JaCoCo 自身的口径是一致的** —— JaCoCo 的行计数里
partly-covered 也算已覆盖行。所以行覆盖率的算法不改，分支覆盖率是并列的第二个数字；
「行 100% / 分支 50%」这个组合正是它要暴露的东西。

### 1.2 四处「同一件事散在多个视图」

| 散落的东西 | 现在在哪几个视图 |
|---|---|
| 被测实例的状态 | `overview` 的「被测实例」表 · `onboard` 的「接入自检」8 行 · `settings` 的「被测实例」+「自检结果」· `events` 的状态变化历史 |
| 门禁结论 | `overview` 的门禁卡 · `gate` 的完整判定 |
| 文件覆盖数据 | `coloring` 的「源文件」列表 · `overview` 的「覆盖率排行」 |
| `overview` 自身 | 389 行，装了门禁 / 趋势 / 实例 / 排行四件不相干的事 |

第一条最伤：想知道「6301 现在到底怎么了」要跑四个视图。

**而加上分支与方法两个指标，第三条会立刻从「重复」变成「冲突」**：新指标放进
「覆盖率排行」就是一张 8 列宽表，放进染色页的文件列表又和排行重了一遍。
这两处必须先合并，指标才有地方落 —— 这是本次页面改动的直接动因，不是顺手整理。

## 二、四种语言实测能拿到什么（2026-08-31 在本机实测）

| | 行 | 分支 | 方法/函数 | 依据 |
|---|---|---|---|---|
| **Java** JaCoCo | ✓ | **✓** | ✓ | `ILine.getBranchCounter()`、`ISourceFileCoverage.getBranchCounter()` / `getMethodCounter()`，全是现成的 |
| **C++** gcov | ✓ | **✓** | ✓ | 加 `-b -c` 后实测 359 条 branch 行、11 条 function 行 |
| **Rust** llvm-cov | ✓ | **✗** | **✓** | 实测 `BRF:0`；`FNF:7`/`FNH` 有值 |
| **Go** covdata | ✓ | **✗** | **✓**（2026-09-02 修正） | 分支：块模型，profile 里只有块的执行次数。方法：`covdata func` 给得出，见下 |

两条硬约束：

1. **Go 给不出分支**。不是没接好，是 coverage profile 里就没有这个信息。
   Rust 要分支得上 nightly 的 `-Z coverage-options=branch`，而本项目是 stable 1.97.1。
2. **C++ 与 Java 的分支口径差一个数量级**（见 §4.2 的实测数字）。

> **2026-09-02 修正：这里原本写的是「Go 永远给不出分支和方法」，方法那半句是错的。**
> 当时只看了 `covdata textfmt` 的输出 —— 那里面确实只有块，没有函数。
> 但 `covdata` 还有一个 `func` 子命令，输出带文件、行号与完全可读的函数名（含接收者）：
> `…/main.go:78:\t*Store.Refund\t0.0%`。做三级钻取报表时实测发现，遂接上。
> **教训是「某个工具给不出 X」这种结论，得把它的子命令都看一遍再下**，
> 而不是看了最常用的那个输出就推广到整个工具。

### 2.1 顺带修正 CLAUDE.md 的一处记录错误

`CLAUDE.md` §四 Rust 一节写的是「它不输出 `BRDA` 分支记录」。
实际是 `llvm-cov export` **默认会导出分支**（因此才有 `--skip-branches` 开关），
只是 rustc stable 的 `-C instrument-coverage` 压根没生成分支数据，所以 `BRF:0`、
一条 `BRDA` 都没有。**结论对，原因记错了** —— 将来有人照着这条去查 lcov 格式会走弯路。

## 四、设计

### 4.1 IR 契约（整个设计的地基）

```java
public record FileCoverage(
    String path, String packageName, String sourceFileName,
    int coveredLines, int missedLines, double ratio,
    Integer coveredBranches, Integer missedBranches,   // 新增
    Integer coveredMethods, Integer missedMethods,     // 新增
    List<LineCoverage> lines
) {
    public record LineCoverage(int line, String status,
                               Integer coveredBranches, Integer missedBranches) {}
}
```

**用 `Integer` 而不是 `int`，`null` 表示「这门语言不提供」。这是整个设计里最要紧的一处。**

`0/0`（有分支这个概念，但这一行没有分支）与 `null`（这门语言根本没有分支概念）
必须分得开。混成 0 的话，页面上 Go 会显示「0% 分支覆盖」——
读的人会以为 Go 的分支一个都没测，而真相是那里压根没有分支这回事。
**这正是本项目最不能接受的那类静默错误：数字是假的，但界面上看不出是假的。**

Java 侧永远不是 `null`（没有分支的行是 `0/0`）；Go 与 Rust 的分支永远是 `null`，
而两者的方法都不是（Go 的方法于 2026-09-02 接上，见 §2 的修正）。

**多实例合并不需要任何额外处理。** 四种语言都是在各自的原生数据层合并
（exec / gcda / profraw），分支与方法计数跟着自动正确 ——
这是当初「不提前退化成行状态再合并」那个决定白捡的好处。

### 4.2 C++ 的分支噪声：为什么分支不做跨语言汇总

在 demo-service-cpp 上实测：

| | 数量 |
|---|---|
| 源码里真正的条件语句（`if`/`&&`/`?:`/`switch`…） | **32 处** |
| gcov 报告的分支 | **359 条** |
| 其中标 `(throw)` 的 | 120 条 |
| 滤掉 throw 后 | **239 条**，仍是源码条件数的 7 倍 |

C++ 里每个可能抛异常的操作（`std::string` 构造、`map` 查找）都会生成分支。
**即使滤掉 `(throw)`，C++ 的分母仍与 Java 差一个数量级。**

因此：

- **滤掉标 `(throw)` 的分支**（编译器为异常路径生成的，不是源码里写的条件），
  保留其余含 `(fallthrough)` 的 —— fallthrough 是条件分支的一个方向，不是噪声；
- **分支不给跨语言总数**，按语言各给各的。同一语言内部纵向可比
  （今天 vs 昨天、这个文件 vs 那个文件），这已经是分支覆盖率真正的用法；
- 页面上那一格要**写明原因**，不能只摆两个数字让人自己去比。

**方法覆盖率仍然汇总**：「一个函数」这个口径在 Java / C++ / Rust 三者间大致一致，
不像分支那样差一个数量级。

### 4.3 采集侧

| 文件 | 改动 |
|---|---|
| `CoverageAnalyzer`（Java） | 行级取 `sf.getLine(i).getBranchCounter()`；文件级取 `sf.getBranchCounter()` / `getMethodCounter()` |
| `CppCoverageAnalyzer` | `runGcov` 加 `-b -c`；`parse` 认 `branch N ...` 与 `function ... called N` 行，滤掉 `(throw)` |
| `RustCoverageAnalyzer` | 认 lcov 的 `FNF` / `FNH`（分支填 `null`） |
| `GoCoverageAnalyzer` | **一行不动**，两项都填 `null`（方法这一项已于 2026-09-02 接上 `covdata func`，见 §2 的修正） |

**一个实现上的坑：gcov 的 `branch` 行不带行号**，它跟在某一条源码行之后。
解析时必须维护「最近一个源码行号」，把 branch 行归到那一行上 ——
按行号解析会全部落空，而表现是「一条分支都没有」，与「这门语言不提供」长得一样。

**Rust 的函数名是 mangled 符号**（`_RNvCs2r1QDoXLnWk_17demo_service_rust6handle`）。
本期只用 `FNF`/`FNH` 的计数，不展示函数名，因此不需要 demangle；
将来若要在页面上列出「哪个函数没测」，再处理。

### 4.4 API

- `summary` 的 `files[]` 每项加 4 个字段；顶层加 `branchesByLanguage`（分语言）与方法汇总；
- `file` 的 `rows[]` 每行加 2 个字段。

**只增字段、不改语义，门禁接口一个字不动。** 因此 `e2e_incremental.py`、
`ws_verify.js` 的门禁断言与 CI 里那句 `curl -f` 都不受影响。

### 4.5 页面

| 视图 | 改动 |
|---|---|
| **overview** | 门禁卡撤掉（`gate` 页已有）· 被测实例表搬走 · 覆盖率排行搬走 · **新增三指标水位卡** · 趋势保留 |
| **coloring** | 文件列表吸收排行的能力（三组数 + 排序 + 导出 CSV）· **源码区行号旁加菱形列** |
| **onboard** | 吸收「被测实例」表，实例状态从此只有这一处 |
| `projects` / `gate` / `events` / `settings` | 不动 |

三指标水位卡：

```
┌─────────────┬──────────────────────┬────────────┐
│  行覆盖      │  分支覆盖             │  方法覆盖   │
│   17.3%     │  Java   62%  18/29   │   12/47    │
│  82/475 行  │  C++    11%  27/239  │   25.5%    │
│             │  Go·Rust  不提供      │            │
└─────────────┴──────────────────────┴────────────┘
```

源码区菱形列：`◆` 绿·分支全跑到 ／ `◈` 黄·只跑了一部分 ／ `◇` 红·一个都没跑。
没有分支的行不显示菱形；Go / Rust 的文件整列不出现（而不是显示一列灰点）。

**菱形与既有的 `PARTIAL` 行状态不是重复表达，两者回答的是不同的问题：**
行底色说的是「这一行执行过没有」，菱形说的是「这一行的分支跑到了几个」。
`PARTIAL` 的定义本来就是「跑过，但行内还有块没跑到」，与「分支部分覆盖」高度重合 ——
**菱形是 `PARTIAL` 的精确化**：原先只能告诉你「这行没跑全」，现在能说清「4 个分支跑了 2 个」。
实现时不要把行底色改成由分支推导，两者各自独立取数。

## 五、核心功能清单新增 #17

分支覆盖率本身是诊断信息，少了平台照常用，按规则 5 的判定标准不该进清单。
**但「Go 显示为不提供而不是 0%」是静默错误防线**，属于本项目「宁可拒绝出报告，
也不出一份静默错误的报告」的一贯取舍，因此新增一条：

| # | 核心功能 | E2E 脚本 | 关键断言 |
|---|---|---|---|
| 17 | 多语言指标能力差异如实呈现 | `scripts/ui_verify.js`、各语言 E2E | 四种语言各自该有的指标有、该缺的明确标为「不提供」而非补零；分支不做跨语言汇总 |

## 八、不做

- **不做指令 / 圈复杂度 / 类覆盖率** —— 只有 Java 有，其余三种语言那几列永远是空的；
- **不让分支进门禁** —— 跨语言不可比，一个统一阈值要么对 C++ 太松要么对 Java 太严；
- **不改菜单结构** —— 七个视图保留，只把散落的东西归位；
- **不为 Rust 上 nightly** —— 为一个诊断指标换掉整条工具链不划算，且 CLAUDE.md 已记录
  Windows 上 Rust 覆盖率环境本就脆弱；
- **不展示函数名** —— Rust / C++ 都是 mangled 符号，要 demangle 才可读，本期只用计数。
